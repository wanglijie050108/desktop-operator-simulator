# 技术决策与风险

## 1. 技术选型决策

### ADR-001：采用 C# Agent + Node Control Server

状态：已被 ADR-007 替代；保留本节作为历史决策记录。

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 全 C# | Windows 集成统一 | Web 自动化和前端迭代较慢，未体现 Node.js 学习目标 | 不选 |
| 全 Node.js | 单语言、Playwright 直接 | Windows UIA、窗口与输入控制能力弱 | 不选 |
| C# + Node.js | 各自负责擅长领域，满足课程要求 | 需要跨进程契约 | 选择 |

边界固定：C# 负责 Windows 桌面执行，Node.js 负责任务编排、浏览器自动化、数据和管理台。

### ADR-002：Playwright 优先于纯鼠标操作浏览器

DOM 选择器可读、可等待、可断言，页面变化时也更容易诊断。纯坐标方式只用于证明底层输入能力，不作为购物主路径。

若站点明确阻止自动化或频繁触发风控，应更换演示站点或使用离线测试夹具，不绕过限制。

### ADR-003：FlaUI(UIA3) 优先于图像识别

状态：实现库选择已被 ADR-007 替代；"语义 UIA 优先于图像和坐标"的原则继续有效，
视觉兜底范围已由 ADR-010 修订（2026-10-10）。

UIA 能获取控件语义、状态和层级，比截图模板匹配更稳定。MVP 不引入 OCR/视觉模型，避免扩大依赖和测试范围。

只有目标控件不暴露 UIA 信息时，才允许加入受分辨率和 DPI 约束的锚点定位，并在每次点击前验证目标窗口。

修订说明（ADR-010）：决策主路径仍为**结构树（UIA/DOM）优先**，此原则不变。但方案 B
需要"截图 + 多模态视觉"作为**兜底**观察手段，用于自绘界面或结构树信息不足的场景。
因此原"MVP 不引入视觉模型"的表述作废：视觉模型可以引入，但不得取代语义定位成为
默认路径，且必须与截图留证、脱敏和 token 预算约束配套。

### ADR-007：Python pywinauto Agent 替代 C# Agent

导师要求 Windows 桌面自动化使用 Python pywinauto。保留 Node.js Control Server、
Vue、SQLite、Playwright 和 WebSocket 1.0 契约，仅替换 Desktop Agent 实现语言。

迁移采用并行代码、单一运行实例：

- `apps/desktop-agent-python` 是目标实现。
- C# Agent 在 Python 达到协议、安全和 Windows 实机验收等价前保留为参考与回退。
- 同一环境不得同时运行两个使用相同 Agent ID 的实现。
- Python 迁移通过后停止默认运行 C#；是否删除 C# 源码另行决策（**已由 ADR-009 收口：
  确定移除 C# 链路，仅保留 Python pywinauto**）。
- 强制守卫（`.trae/skills/human-operation-simulator-guardrails/SKILL.md` §3/§5/§6）已同步为
  Python 3.11 + pywinauto 口径，并保留"迁移期 C# 契约回归"要求（2026-10-04）。

选择该方案是因为真实 FlaUI Adapter 尚未开发，当前 C# 资产主要是协议与可靠性逻辑；
重用语言无关契约和 Node 控制平面，比整仓重写风险更低。

### ADR-008：C# Agent 冻结保留（不删除、不发展）

状态：**已由 ADR-009 撤销**；收口 ADR-007 第 41 条"是否删除 C# 源码另行决策"（原结论为冻结保留，现由 ADR-009 改为确定移除）。保留本节作为历史决策记录。

原决策内容（**已失效，仅作历史**）：

- Windows 桌面自动化的唯一实现方向是 Python 3.11 + pywinauto；`apps/desktop-agent-python`
  是唯一目标实现，也是唯一在此方向上继续开发的位置。
- C# `apps/desktop-agent` **冻结保留**：不删除，也不新增任何桌面动作、UIA/FlaUI 实现或
  其它 Windows 自动化；其占位执行器继续对所有动作返回 `NOT_IMPLEMENTED`。
- **不把 .NET 加回日常质量门**：`npm run check` 只依赖 Node.js 与 Python；C# 的格式、
  构建、单测与进程集成回归由 CI 的 `dotnet` job 与 `npm run check:all` 承担。
- 保留理由：C# 的维护成本已被隔离（不参与业务路径、不参与日常门），但仍提供两项收益——
  共享 fixture 的跨语言契约不漂移，以及 pywinauto 路线出现问题时存在可执行回退基线。
- 复查触发条件（已失效）：原定 M2/M3 实机验收完成后评估删除。现于 2026-10-09 提前决定移除
  C# 链路，详见 ADR-009；以下清理项已纳入 ADR-009 的执行范围：`HumanOperationSimulator.slnx`、
  `Directory.Build.props`、`global.json`、CI `dotnet` job、`check:dotnet` / `check:all` /
  `test:integration:m1:csharp`、`apps/desktop-agent/**` 以及共享 fixture 的 C# 消费测试。
- 守卫 §3 与本决策一致：不在 C# Agent 中新增 Windows 自动化，也不把 FlaUI 工作视为计划内。

失效说明：上述"C# 资产现存""CI 的 `dotnet` job 与 `check:all` 承担 C# 质量门"的描述
在 ADR-009 执行后已不成立——C# 工程文件、`dotnet` job 与 `test:integration:m1:csharp`
均已移除，`npm run check:all` 现与 `npm run check` 等价且不含任何 .NET 步骤。

### ADR-009：移除 C# Agent 链路

状态：已决定（2026-10-09）；替代 ADR-008 的"冻结保留"结论。

- Windows 桌面自动化的唯一实现方向是 Python 3.11 + pywinauto；`apps/desktop-agent-python`
  是唯一目标实现，也是唯一继续开发的位置。
- 确定移除 C# `apps/desktop-agent` 及其工程文件（`HumanOperationSimulator.slnx`、
  `Directory.Build.props`、`global.json`、CI `dotnet` job、`check:dotnet` /
  `test:integration:m1:csharp`），不再保留为参考实现或回退基线。
- 共享 `contracts/fixtures/websocket-v1/messages.json` 的契约证据由 Node 与 Python 继续维护，
  移除 C# 消费测试。
- `npm run check` 维持仅依赖 Node.js 与 Python；CI 的 `dotnet` job 移除。`npm run check:all`
  不再包含任何 .NET 步骤，实际保留为与 `npm run check` 等价的 Node + Python 兼容入口
  （未删除；2026-10-09 的执行结果以 `package.json` 与 `changelog/2026-10-09-remove-csharp-agent-chain.md` 为准）。
- 决策动机：C# 链路长期不参与业务路径与默认运行；在 pywinauto 路线已达协议、安全与基础
  动作验收等价后，继续保留 C# 基线已无净收益。
- 风险与缓解：失去可执行回退基线；以共享 fixture 的跨语言契约与 Python 自测覆盖缓解。

### ADR-010：引入 LLM 决策层，采用有界自主循环（方案 B）

状态：已决定（2026-10-10）；取代 ADR-005，并部分修订 ADR-003 与 ADR-002 的适用范围。

**决策**：在 Control Server 内引入 observation → reasoning → action 决策循环，由 LLM
根据结构树（UIA/DOM）观察（截图 + 多模态视觉为兜底）自主提议下一个白名单桌面动作。
详细设计见 [`14-plan-b-design.md`](14-plan-b-design.md)。

关键约束（这些约束不可协商，任何实现不得绕过）：

1. **LLM 只提议，不执行**。LLM 输出结构化动作提议，必须依次通过 JSON Schema、动作
   白名单、参数范围、策略引擎与目标进程/域名允许列表校验；任一步失败即丢弃该提议，
   不做"尽力修正"。
2. **LLM 无特权**。LLM 不得产生代码、脚本、文件路径、URL 跳转或直接发给用户的文本；
   不具备任何形式的内存、文件或网络访问能力。
3. **成功由确定性 verifier 判定**。LLM 自述"任务完成"不构成成功；必须由确定性后置
   条件（如候选通过现有预算过滤与字段校验）判定。
4. **决策循环有界**。每任务设轮次、wall-clock 与 token 三重预算；达到上限转
   `WAITING_FOR_HUMAN`，不允许无界循环。
5. **观察内容是不可信数据**。网页与聊天内容可能包含提示注入，防线为"标记为数据 +
   LLM 无权限 + 动作白名单 + 策略双检 + 禁止动作清单"，不得依赖提示词本身健壮。
6. **全量留痕与可回放**。每轮 observation 摘要、模型输出、校验结论与执行结果持久化
   并脱敏，支持用录制轨迹回放，以约束非确定性。
7. **安全红线不因引入 LLM 而放宽**：支付、转账、下单确认、凭据与 Cookie 提取、
   验证码与风控绕过、任意脚本执行、跨进程读写他人进程内存一律禁止。
8. **保留确定性快捷路径**：原八步商品工作流降级为"有把握时走的路径"，用于演示兜底
   与回归对照，不再作为唯一执行路径。

决策动机：课程目标是"由程序代替人操作没有 API 的软件"，需要一个能应对未见界面的
决策层；而现有仓库已把动作基元、白名单、双重策略、幂等、超时、急停与留证全部建好，
LLM 决策层可以建立在其上而不削弱既有安全边界。

风险与缓解：

- 非确定性导致验收与演示不稳定 → 决策轨迹回放、确定性快捷路径兜底、轮次预算。
- 提示注入升级为一等威胁 → 上述第 5 条的分层防线，并新增专门的注入测试用例。
- 成本与延迟上升 → 三重预算 + 模型选择可配置（环境变量），统计每任务决策轮数与
  token 消耗。
- 观察层能力不足（自绘界面不暴露 UIA）→ 视觉兜底路径；微信 4.1.15.13 仍需按
  ADR-011 单独选型。

### ADR-011：微信 4.1.15.13 不作为演示通道

状态：已决定（2026-10-10）。

- 实测该版本在 UIA（含 Raw View）、MSAA 与 Win32 下只暴露顶层窗口 + 2 个容器 Pane，
  取不到会话、消息与输入框；社区可行路线（写 `Weixin.dll` 标志位热激活、跨进程读内存
  解密本地库）均超出本项目安全边界。
- 决策：**不采用跨进程读写内存的路线**；聊天入口通道本期不解决，决策层与通道解耦，
  先用本地/模拟入口驱动完整闭环（见 `docs/14` §1 D6）。
- 后续若需真实通道：优先降级到原生暴露 UIA 控件的微信 3.9.x，或更换为其它可访问的
  聊天工具，需单独评估后另立 ADR。

### ADR-004：SQLite 优先于 PostgreSQL

系统首期只运行一台代理机、任务默认串行，SQLite 足以支持事务、持久化和查询。它减少部署工作，适合课程项目。出现多代理并发调度或远程部署需求时再评估 PostgreSQL。

### ADR-005：确定性工作流优先于自主 Agent

状态：**已被 ADR-010 取代**（2026-10-10）。保留本节作为历史决策记录。

原决策：AI 输出存在不稳定和提示注入风险，因此 AI 只解析候选参数或生成摘要。动作顺序由代码定义，所有动作必须通过 Schema 和策略校验。首期不采用可自由调用工具的 ReAct/多智能体框架。

被取代的原因：课程目标要求"由 AI 模拟人的操作"，即代理需在未见过的界面下自主决定
"点哪里、复制什么"。纯确定性工作流无法满足该目标（详见
[`13-architecture-fit-analysis.md`](13-architecture-fit-analysis.md) 与
[`14-plan-b-design.md`](14-plan-b-design.md)）。**原决策中"所有动作必须通过 Schema 和
策略校验"这一条继续有效，并由 ADR-010 保留。**

### ADR-006：本地单机部署优先

用户通过聊天工具远程发指令，控制服务无需公网暴露。单机部署也避免把账号会话、截图和自动化权限上传云端。

## 3. 开工前必须确认的产品决策

以下信息在任务书中缺失，不阻塞 M0 Spike，但必须在 M1 前冻结：

1. 目标聊天工具及确切版本，默认按 Windows 微信桌面端设计。
   （**已决定：本期不解决聊天入口通道，见 ADR-011 与 `docs/14` §1 D6**）
2. 目标 AI 页面和购物站点。
3. 代理机 Windows 版本、分辨率、DPI 和是否允许独占桌面。
4. 是否允许保存专用测试账号的本地浏览器会话。
5. 商品“最优”的评分权重及缺失字段处理方式。
6. 是否需要加入购物车；建议不纳入 MVP。
7. 管理台是否仅本机使用；建议首期仅本机。

### 3.1 已冻结的决策（2026-10-10，见 ADR-010 / `docs/14`）

- **AI 角色**：方案 B，LLM 在 Control Server 内驱动有界自主循环。
- **决策循环位置**：Control Server（Node 侧）；Python Agent 保持只执行白名单动作。
- **观察手段**：结构树（UIA/DOM）为主，截图 + 多模态视觉为兜底。
- **模型来源**：国内 API（DeepSeek / 通义等），OpenAI 兼容协议，环境变量配置。
- **商品链路操作层面**：桌面 GUI，AI 用鼠标键盘操作浏览器。
- **LLM 权限**：只提议白名单动作，无执行权、无代码/文件/网络能力。
- **成功判定**：确定性 verifier，LLM 自述完成不算成功。
- **意图解析边界（D10）**：受理判定由规则完成；仅对正则解析失败的消息追加**一次**
  LLM 解析尝试，结果走业务范围与策略校验（`docs/14` §1.1）。
- **打开目标应用（D11）**：**不新增"启动进程"类动作**，Agent 只接管已运行的白名单
  窗口；M6 的真实环境验证与演示由人工/启动脚本预先打开浏览器与 AI 页面
  （`docs/14` §1.2）。全自动"从零启动到完成"不在本期承诺范围。
